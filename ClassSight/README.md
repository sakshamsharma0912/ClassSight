# ClassSight

**Track performance. Guide progress.**

ClassSight is a Flask, SQLite and Tailwind CSS application with separate teacher and student workspaces. Student analysis
is the main experience: class averages, subject charts, grade distribution, academic
pass rates, risk flags, student comparisons and live improvement simulations.
University attendance registers, component marks and department reports support
that analysis. The newer institutional light theme, navy navigation, slate headings
and teal accents are retained. Graphs use local HTML/SVG and work without a chart CDN.

This is an independent academic project using SRMIST course references. It
does not connect to university SSO, access official student records, or issue
university-authorized documents. The signed-in SRM portal screens were not
available for visual comparison. Reports and notices are generated by the
local faculty account for review and signature.

## Run on Windows

1. Install Python **3.10 or later** and extract this ZIP.
2. Open the extracted **ClassSight** folder.
3. Double-click **run.bat**.
4. Open **http://127.0.0.1:5000** and register a teacher account.

The launcher creates a virtual environment and installs the pinned Python
dependencies. Internet is needed for the first installation; after installation,
the application and compiled styles work locally without a CDN.

There is no default administrator password. Sixteen **fictional** students in
CSE-A and CSE-B are initialized with seven course records each. The seeded
names and registrations beginning CSE25 are demonstration data, not a real
class roster. Faculty workspaces are isolated; another account cannot view,
change, or download your records.

On macOS/Linux, run `bash run.sh`. For a manual launch:

```bash
python -m venv .venv
# Windows: .venv\\Scripts\\activate
# macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
python app.py
```

Stop with Ctrl+C. Set PORT to use another port. The local launcher binds
127.0.0.1 and runs with debug mode off.

## Teacher and student login

Choose **Teacher** or **Student** on the sign-in screen. The server checks credentials against the selected account type and routes a successful login accordingly:

|Route|Access and data scope|
|-|-|
|`/teacher/dashboard`|Teacher-owned batch insights with section, admission-batch, course and attendance filters|
|`/student/dashboard`|Only the academic record linked to the signed-in student account|
|`/student/reports`|Personal report choices; PDF, Excel and CSV include that student's course records only|
|`/student/settings`|The student's read-only roster identity and password change|
|`/dashboard`|Compatibility redirect to the authenticated account's correct dashboard|

### Give a student login access

1. Register or sign in as a teacher and open a student from **Student directory**.
2. Choose **Student access**, enter the student's login email and select **Create activation link**.
3. Copy the link and share it directly with that student. It expires in **48 hours** and can be used once. Generating a new link invalidates the outstanding link.
4. The student opens the link while signed out, chooses a password and enters `/student/dashboard`. To test on one computer, use a private browser window or another browser.
5. Later, choose **Student** on the login page and sign in with the activated email and password.

No default student passwords are supplied. Registration numbers alone cannot claim an existing record. The server binds activation to the roster entry selected by its owning teacher; posted role, email or student-reference changes cannot redirect that binding.

Students see their own course graph, marks, grade, performance flags, attendance margins, original subject results where present, and both what-if simulators. Class averages, rankings, student lists and batch analytics are teacher views. Student academic records are read-only; sliders are temporary scenarios. Student accounts cannot change marks/attendance, import rosters, issue letters, create invitations or download faculty/class exports, including by manually entering those URLs.

**Revoke student access** signs out that student's sessions and invalidates pending links without deleting academic records. A newly activated replacement link can restore access or reset a student's password. Password changes and replacement activation invalidate other student sessions. Deleting the roster entry also removes its account and invites.

The default server address is local to your computer. A student on another device needs an appropriately configured shared deployment; a localhost activation link works only on the computer running the app. No email is sent automatically.

## Student analysis and what-if rules

* Course charts average only completed course evaluations. Component heatmaps
average only entered values and normalize each component against its own maximum.
* Overall student grade and rank require every selected course to be fully evaluated.
An evaluated average may still be shown for a partially assessed student, with an
explicit evaluated-course count. Unentered marks never become zero in saved results.
* Academic pass requires 40/100 in every selected course. Pass rate uses fully
evaluated students as its denominator; attendance eligibility is separate.
* The original analyzer's risk thresholds are retained: **At Risk** for a completed
course below 40, evaluated average below 50, or course attendance below 75%.
**Watchlist** applies to an evaluated average below 65 or eligible course attendance
below 85%. Otherwise incomplete records are **Pending**, or complete records are
**On Track**. These support flags are project rules, not an official detention order.
* Overall averages use equal course weighting, not credit-weighted GPA/CGPA. Rank is
competition rank among fully evaluated students in the current class scope; ties
share a rank. Profile ranks compare the same section and admission batch.
* Charts follow name/search, section, batch, course and attendance filters. Grade,
performance and sort filters narrow the student table and its performance CSV.
* The overall simulator starts each course at its saved total, or known subtotal
if evaluation is incomplete. Those are explicitly temporary scenarios. It raises
the lowest course totals to meet an average target, without lowering existing
totals, exceeding 100 or leaving any course below 40. Attendance stays fixed.
* The component simulator keeps the exact seven-component order and 60/40 internal/
final split. Neither simulator saves marks; actual marks use the evaluation forms.
* Earlier three-subject archives keep the original A+/A/B/C/D/E/F scale and original
thresholds. Those marks are never silently mapped to university components or hours.

## Attendance calculations

For one course, let T = conducted/max hours and A = attended hours.

|Value|Calculation / meaning|
|-|-|
|Absent hours|T − A|
|Percentage|100 × A / T; Not started when T = 0|
|Required hours now|ceil(3T / 4)|
|Current signed margin|A − ceil(3T / 4); green buffer, red deficit|
|Future hours that can be missed|floor((4A − 3T) / 3), when eligible|
|Consecutive recovery hours|3T − 4A, when below 75%|
|Attendance eligibility|T > 0 and 4A ≥ 3T, before display rounding|

74/100 is 74%, with a **−1 current-hour margin**. Four consecutive attended
hours recover 75% because 78/104 = 75%. Current shortage and future recovery
are different quantities. Future recovery assumes all additional hours are
attended and enough classes remain.

75% is checked **per course**. A class/overall percentage above 75% cannot
clear a low course. Summary totals are **student-hours**, not faculty teaching
load. The percentage is weighted by recorded hours; summary margins sum the
individual course margins.

Below 75% indicates current shortage and detainment risk. The portal does
not automatically apply institutional condonation or certify final detention.
Zero-hour records are Not started, never falsely eligible or detained.

## Assessment — exact order

|Order|Component|Maximum|
|-|-|-:|
|1|Assignment 1|5|
|2|Assignment 2|5|
|3|Internal Exam 1|15|
|4|Mini Project|10|
|5|Practical|10|
|6|Internal Exam 2|15|
|7|University Final Exam|40|
||Internal total|60|
||Course total|100|

Values accept up to two decimal places and are stored as integer centimarks:
4.99 = 499. Exact grade boundaries and caps do not depend on floating-point
rounding. Blank values are SQL NULL; assessed zero is zero. A grade is computed
only when all seven components are entered. Partial internal totals are identified.

Configured grade bands: O ≥90, A+ ≥80, A ≥70, B+ ≥60, B ≥50, C ≥40, F <40.
Attendance and marks are separate: high marks do not clear an attendance shortage.

The simulator uses zero for unentered marks in its temporary projection.
It never saves slider movement. “Edit saved marks” opens the actual persistence
form. If a target exceeds the final-exam cap, the internal improvement required
is shown.

## CSV workflow

```csv
student\_id,name,section,batch,course\_code,max\_hours,attended\_hours,assignment\_1,assignment\_2,internal\_exam\_1,mini\_project,practical,internal\_exam\_2,university\_final
CSE25D101,Aditi Sharma,CSE-D,2025-2029,21CSC201J,40,32,4,5,12,8,9,11,
```

* One row represents one student/course. Repeat a student with another course
code, keeping the same name, section and batch.
* Creating a student creates seven enrollments. Other courses start with zero
hours and pending marks.
* Existing students are rejected by default. Update existing course records
replaces the supplied course values, including blanks. Name, section and batch
must match the profile; edit the profile first if those need to change.
* Headers may be reordered and are case-insensitive. No extra, missing or
duplicate columns are accepted.
* The whole file, up to 2 MB / 1,000 course rows, is validated before one
transaction saves it. Any invalid row or later conflict rolls back everything.
* Duplicate student/course rows, unknown courses, invalid batches, fractional
hours, excess marks, bad encoding and inconsistent profiles are rejected.
* Directory **Export CSV** is the round-trip import format. **Report CSV**
includes derived values and a cumulative summary and is for reporting.
* CSV and Excel text fields are protected against spreadsheet formula injection.

Both the template and multi-course example are in **examples/**.
The earlier six-column Maths/Science/English/Attendance CSV is accepted as an
archived result; the app does not invent course components or conducted hours.

## Upgrade your existing database

The database remains **instance/analyzer.sqlite3**, matching the earlier project.

1. Stop the old server and keep your own backup of its instance folder.
2. Extract the new source separately.
3. Copy the old **instance/analyzer.sqlite3** and **instance/secret.key** into
the new project's instance folder.
4. Start the upgraded server. Existing faculty accounts retain their IDs and records; the student-account and invitation tables are added automatically.

When the old three-subject schema is detected, migration:

* Makes a physical SQLite backup named
`analyzer.sqlite3.v1-backup-<timestamp>`.
* Retains faculty IDs, emails, password hashes, student primary keys,
registration numbers and names.
* Preserves original rows in legacy\_students\_v1 and legacy\_results and
displays archived subject results on the student page.
* Creates seven blank course records; genuine component marks and hours
must be entered/imported because the earlier totals cannot reveal them.
* Uses initial CSE-A / 2025-2029 profile values because the old schema had
neither section nor batch; review these after migration.

Migration is transactional and runs once. Deleting a roster and restarting
does not reseed it. Fresh faculty accounts receive their own fictional roster.
For an empty workspace in code, use `create\_app({"SEED\_DEMO": False})`.

## Reports and shortage letters

Downloads follow the visible section, batch, course, name/registration search
and attendance filters. A student's academic report uses its exact database
reference, so similarly prefixed registration numbers are not included.

* **PDF** includes institution/campus/department, year/semester/preparer,
the attendance register and aggregate student-hours, ordered assessment
components, grade rules, repeated table headers and review signature areas.
* **Excel** includes Report, Attendance and Marks sheets, frozen headers,
filters, numeric values, print settings and shortage highlighting.
* **Report CSV** includes derived attendance and mark fields and a summary row.
* **Shortage notice** includes current course attendance, signed margin,
recovery estimate, issue reference and faculty review/signature fields.

Issuing a notice is a CSRF-protected POST and stores the complete attendance,
student and faculty snapshot. Later downloads preserve that snapshot even
after attendance updates or student deletion. Session snapshots also survive
later roster changes.

## Security and operating notes

Server-side account roles and ownership checks protect records and exports. Student queries are constrained to the account-linked student primary key, never a student ID or teacher ID from a URL. Activation tokens are stored as SHA-256 hashes; student passwords use Werkzeug scrypt hashes. Revocation and password reset use account versions to invalidate prior student sessions. Writes require session CSRF tokens.
SQL uses bound parameters, Jinja escapes content, Werkzeug stores scrypt
hashes, and responses include restrictive security headers. Bulk saves use
record versions to reject stale forms and accidental overwrites.

The local secret is privately generated as **instance/secret.key**.
For hosted HTTPS, set an unpredictable SECRET\_KEY of at least 32 characters,
APP\_HTTPS=1, and use an appropriate WSGI server. The launcher is for local use.
Do not enable secure cookies on plain-HTTP localhost or sessions will fail.
Keep the runtime database, secret and backups private and out of source control.

There is no email sending or live SRM synchronization. If port 5000 is busy,
set another PORT. If a form reports a stale version, reload it. Import errors
identify the line/problem and leave the database unchanged.
